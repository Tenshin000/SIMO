\section{Introduzione}
\subsection{Problem Statement \& Contesto di Dominio}
Nei moderni processi di preparazione culinaria professionale e di alta pasticceria, la gestione delle ricette presenta una complessit\`a computazionale e strutturale che eccede ampiamente le capacit\`a di un semplice archivio testuale o tabellare.

I requisiti critici individuati sul campo evidenziano le seguenti problematiche:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Gerarchie Multi-Livello (Composite Recipes):} Le preparazioni complesse non sono insiemi piatti di materie prime, bens\`i aggregati di preparazioni intermedie (\textit{sotto-ricette}). Ad esempio, un \textit{Cornetto alla Crema} include una pasta sfogliata lievitata e una \textit{Crema Pasticcera}. Qualsiasi variazione della resa o della ricetta base della crema deve propagarsi in modo deterministico e reattivo all'intero albero di composizione;
    \item \textbf{Inversione di Scala da Vincolo di Dispensa (Reverse Scaling):} In ambiente di laboratorio o domestico, la quantit\`a di resa finale \`e frequentemente vincolata dalla disponibilit\`a residua di un ingrediente critico (esempio: 120\,g di burro anzich\'e 175\,g). Il sistema deve essere in grado di calcolare il fattore di scala inverso $k \in \mathbb{R}^+$ rispetto a un generico nodo dell'albero ed estendere la proporzione all'intero grafo;
    \item \textbf{Tracciabilit\`a Normativa degli Allergeni (Regolamento UE 1169/2011):} L'obbligo di legge impone l'individuazione e la segnalazione dei 14 allergeni normativi. La presenza di un allergene in una foglia del grafo deve essere propagata ricorsivamente fino alla radice;
    \item \textbf{Food Cost Contabile in Tempo Reale:} Necessit\`a di quantificare all'istante l'incidenza economica di ciascun lotto di produzione e il costo industriale di ogni singola porzione, considerando conversioni tra unit\`a di massa ($g, kg$), di volume ($ml, l$) e unit\`a discrete quantizzate ($pezzi; unit\grave{a}$);
    \item \textbf{Operativit\`a Senza Soluzione di Continuit\`a (Cooking Mode):} Esigenza di un'interfaccia esecutiva durante la cottura che mantenga il display costantemente attivo, gestisca timer asincroni multipli con allarmi acustici e vibrazione, e supporti aggiunte rapide di tempo non intrusive;
    \item \textbf{Privacy e Sicurezza delle Chiavi API di Terze Parti:} Protezione crittografica hardware-backed contro attacchi di estrazione locale o perdite accidentali nei backup per le chiavi di accesso a modelli generativi remoti (Google Gemini e OpenAI ChatGPT);
    \item \textbf{Variazione di Massa Termica in Cottura (Resa Termica \& Calo Peso):} Nei trattamenti termici (cottura in forno, padella, bollitura, frittura) gli alimenti subiscono alterazioni fisiche rilevanti della massa: calo peso per evaporazione dell'acqua (es. torte, arrosti $-10\% \div -20\%$) oppure aumento di massa per assorbimento di liquidi idratanti (es. pasta secca e riso $+100\% \div +150\%$). L'architettura deve modellare tale fenomeno termodinamico calcolando la resa cotta finita a porzione e la conseguente variazione di densit\`a dei nutrienti;
    \item \textbf{Dichiarazione Nutrizionale Ufficiale (Regolamento UE n. 1169/2011):} Necessit\`a di determinare in modo scientifico la concentrazione o diluizione post-cottura dei 6 nutrienti normativi (Energia in kJ/kcal, Grassi, Carboidrati, Proteine, Acqua, Sodio e Sale equivalente), fornendo la doppia rappresentazione analitica \textit{Per 100g} e \textit{Per Porzione} contrassegnata dalla dicitura legale di stima.
\end{enumerate}

\subsection{Requisiti Non Funzionali e Vincoli Architetturali}
Il sistema \`e stato ingegnerizzato rispettando i seguenti vincoli prestazionali e architetturali:
\begin{itemize}[leftmargin=*]
    \item \textbf{Offline-First:} Tutte le funzioni analitiche, di scaling, di navigazione del grafo, di food cost e di cottura guidata devono operare a latenza zero anche in assenza totale di connettivit\`a di rete;
    \item \textbf{Tempo di Calcolo dello Scaling:} Complessit\`a temporale $O(|V| + |E|)$ rispetto al grafo di composizione, con tempo di re-rendering $\le 16\,\text{ms}$ a 60\,FPS per evitare frame-drop nell'interfaccia utente dichiarativa;
    \item \textbf{Assenza di Dipendenze Circolari:} Garanzia formale che il grafo delle ricette rimanga in ogni istante un \textbf{Grafo Diretto Aciclico} (\textbf{DAG});
    \item \textbf{Memory Footprint Controllato:} Nessuna allocazione ridondante di bitmap durante l'esportazione PDF o la gestione dei timer; rilascio immediato delle risorse audio dell'Hardware Abstraction Layer.
\end{itemize}

\subsection{Unidirectional Data Flow (UDF) e State Immutability}
Ogni schermata applicativa \`e funzione pura dello stato corrente (\textit{State-Driven UI}):
$$\text{UI} = f(\text{UiState})$$
I ViewModel non espongono variabili mutabili pubbliche: ogni transizione di stato avviene tramite istanze di data class immutabili incapsulate in \texttt{StateFlow<T>}.

\begin{lstlisting}[caption={Esempio di emissione di stato reattivo in RecipeListViewModel}]
val uiState: StateFlow<RecipeListUiState> = combine(
    repository.allRecipes,
    _filterState
) { recipes, filter ->
    // Calcolo filtri, ordinamento e ricerca su pool di background
    val sortedAvailableTags = RecipeTags.getAllSortedTags(recipes.map { it.category })
    val byTags = if (filter.selectedTags.isEmpty()) recipes 
                 else recipes.filter { r -> filter.selectedTags.any { it.equals(r.category, true) } }
    val byFavorites = if (filter.favoritesOnly) byTags.filter { it.isFavorite } else byTags
    val filtered = if (filter.query.isBlank()) byFavorites 
                   else byFavorites.filter { it.name.contains(filter.query, true) }
    
    
    
    val sorted = when (filter.sort) {
        RecipeSortOption.NAME_ASC -> filtered.sortedWith(compareBy(String.CASE_INSENSITIVE_ORDER) { it.name })
        RecipeSortOption.NAME_DESC -> filtered.sortedWith(compareByDescending(String.CASE_INSENSITIVE_ORDER) { it.name })
        RecipeSortOption.DATE_DESC -> filtered.sortedByDescending { it.createdAt }
        RecipeSortOption.DATE_ASC -> filtered.sortedBy { it.createdAt }
    }
    RecipeListUiState(recipes = sorted, availableTags = sortedAvailableTags, ...)
}.flowOn(Dispatchers.Default)
 .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), RecipeListUiState())
\end{lstlisting}

\subsection{Concorrenza e Thread Safety}
L'applicazione fa uso sistematico delle Kotlin Coroutines, assegnando rigorosamente i contesti di esecuzione:
\begin{itemize}[leftmargin=*]
    \item \textbf{\texttt{Dispatchers.Main}:} Riservato esclusivamente al rendering dichiarativo di Jetpack Compose e al binding degli eventi UI;
    \item \textbf{\texttt{Dispatchers.Default}:} Dedicato al calcolo analitico intensivo (espansione del DAG, determinazione dei percorsi, ordinamento, estrazione regex dei timer e ricalcolo proporzionale);
    \item \textbf{\texttt{Dispatchers.IO}:} Adibito all'I/O su database Room SQLite, operazioni di crittografia hardware, chiamate REST HTTP di Gemini e stream di scrittura PDF/JSON.
\end{itemize}

\subsection{Lifecycle Optimization: Warm-up Asincrono e Pre-caching all'Avvio}
Per prevenire l'anti-pattern del \textit{Flash of Empty State} (in cui la schermata home mostra un layout vuoto per alcune centinaia di millisecondi durante l'interrogazione asincrona iniziale del database), l'architettura implementa una fase di warm-up reattivo. 
Durante lo splash iniziale di avvio, il repository esegue il pre-caricamento immediato della collezione completa delle entit\`a \texttt{RecipeWithComponents}. L'emissione iniziale del relativo \texttt{StateFlow} avviene in modo concorrente con la composizione della UI, garantendo che al passaggio alla schermata del ricettario l'elenco sia gi\`a interamente popolato e ordinato, azzerando qualsiasi percezione di caricamento differito.

\section{Domain Engine: Teoria dei Grafi e Calcolo Matematico}
Il nucleo algoritmico risiede nel file \texttt{MathEngine.kt}, implementato come modulo Kotlin puro privo di dipendenze verso il framework Android.

\subsection{Formalizzazione del Ricettario come DAG Pesato}
\begin{definition}[Grafo delle Ricette]
Sia $G = (V; E; W)$ un grafo orientato pesato finito dove:
\begin{itemize}
    \item $V = V_{\text{raw}} \cup V_{\text{recipe}}$ \`e l'insieme dei vertici, partizionato in materie prime $V_{\text{raw}}$ e preparazioni composte $V_{\text{recipe}}$.
    \item $E \subseteq V_{\text{recipe}} \times V$ \`e l'insieme degli archi orientati $(u; v)$, indicante che la ricetta $u$ richiede l'ingrediente o sotto-ricetta $v$.
    \item $W: E \to \mathbb{R}^+ \times \mathcal{U}$ \`e la funzione peso che associa ad ogni arco la tupla $(q; u)$ rappresentante la quantit\`a base $q$ e l'unit\`a di misura $u \in \mathcal{U}$.
\end{itemize}
\end{definition}

Affinch\'e il calcolo delle dosi converga in tempo finito e non generi paradossi fisici (ad esempio: la Crema Pasticcera che richiede Cornetti che a loro volta richiedono Crema Pasticcera), $G$ deve soddisfare il vincolo fondamentale di aciclicit\`a:
$$\forall v \in V, \quad \nexists \text{ cammino orientato } v \rightsquigarrow v \quad \iff \quad G \text{ \`e un DAG}$$

\subsection{Algoritmo di Rilevamento Cicli Preventivo (\texttt{wouldCreateCycle})}
Prima di consentire l'inserimento o la modifica di un arco $(u; v)$ dove $u$ \`e la ricetta genitore e $v$ \`e la ricetta figlia candidata, il sistema valuta se esiste un cammino diretto $v \rightsquigarrow u$.

\begin{theorem}[Condizione di Aciclicit\`a su Inserimento di Arco]
Dato un DAG $G = (V; E)$ e un arco candidato $(u; v)$, il nuovo grafo $G' = (V; E \cup \{(u; v)\})$ \`e un DAG se e solo se $u$ non \`e raggiungibile da $v$ in $G$.
\end{theorem}
\begin{proof}
Se $u$ fosse raggiungibile da $v$, esisterebbe un cammino orientato $p = (v; w_1; w_2; \dots; w_k; u)$ in $G$. Aggiungendo l'arco $(u; v)$, si formerebbe il ciclo $C = (u; v; w_1; \dots; w_k; u)$, violando la propriet\`a di DAG. Se $u$ non \`e raggiungibile da $v$, nessun nuovo cammino originante da $u$ potr\`a mai ricongiungersi a un suo predecessore, preservando l'aciclicit\`a.
\end{proof}

L'implementazione in \texttt{MathEngine.kt} impiega una Breadth-First Search (BFS) ottimizzata:
\begin{lstlisting}[caption={Algoritmo BFS per la validazione aciclica di nuovi componenti}]
fun wouldCreateCycle(
    parentRecipeId: String,
    candidateChildId: String,
    existingEdges: List<Pair<String, String>>
): Boolean {
    if (parentRecipeId.isBlank() || candidateChildId.isBlank()) return false
    if (parentRecipeId == candidateChildId) return true // Auto-loop immediato

    // Costruzione lista di adiacenza
    val adjacency = mutableMapOf<String, MutableList<String>>()
    for ((parent, child) in existingEdges) {
        if (parent.isNotBlank() && child.isNotBlank()) {
            adjacency.getOrPut(parent) { mutableListOf() }.add(child)
        }
    }

    val queue = ArrayDeque<String>()
    queue.add(candidateChildId)
    val visited = mutableSetOf<String>()

    while (queue.isNotEmpty()) {
        val curr = queue.removeFirst()
        if (curr == parentRecipeId) return true // Ciclo rilevato!
        if (visited.add(curr)) {
            adjacency[curr]?.forEach { next ->
                if (!visited.contains(next)) queue.add(next)
            }
        }
    }
    return false
}
\end{lstlisting}
\textbf{Complessit\`a Computazionale:}
\begin{itemize}
    \item \textbf{Tempo:} $O(|V| + |E|)$ nel caso peggiore (visita di tutti i vertici e archi raggiungibili).
    \item \textbf{Spazio:} $O(|V|)$ per l'allocazione della coda e dell'insieme di visitati.
\end{itemize}

\subsection{Algoritmo di Espansione ad Albero Scalato (\texttt{buildScaledTree})}
Dato un nodo radice $R \in V_{\text{recipe}}$ e un target di resa $Y_{\text{target}} \in \mathbb{R}^+$, il fattore di scala primario $k_R$ \`e calcolato come:
$$k_R = \frac{Y_{\text{target}}}{Y_{\text{base}}(R)}$$

Per ciascun componente $c = (R, i)$ con quantit\`a base $q_{\text{base}}(c)$:
$$q_{\text{scaled}}(c) = q_{\text{base}}(c) \cdot k_R$$

Se il componente $i$ \`e a sua volta una ricetta $i \in V_{\text{recipe}}$, essa richiede una quantit\`a pari a $q_{\text{scaled}}(c)$ espressa nell'unit\`a di resa della sotto-ricetta. Di conseguenza, il fattore di scala per la sotto-ricetta $k_i$ diventa:
$$k_i = \frac{q_{\text{scaled}}(c)}{Y_{\text{base}}(i)} = \frac{q_{\text{base}}(c) \cdot k_R}{Y_{\text{base}}(i)}$$
Il processo prosegue ricorsivamente fino alle foglie del grafo ($V_{\text{raw}}$).

\begin{archbox}[Protezione da Stack Overflow su Ricorsione Profonda]
Per garantire la robustezza del runtime Android e prevenire esaurimenti di stack su grafi patologici, l'algoritmo impone una soglia massima di guardia \texttt{MAX\_RECURSION\_DEPTH = 25} e mantiene un set di controllo \texttt{visitedRecipeIds} ad ogni ramo dell'albero.
\end{archbox}

\subsection{Modello di Reverse Scaling}
Il Reverse Scaling consente di calcolare il moltiplicatore $k^*$ a partire da un generico ingrediente $j$ per cui l'operatore dispone di una quantit\`a limite $q_{\text{disp}}(j)$:
$$k^* = \frac{q_{\text{disp}}(j)}{q_{\text{base}}(j)}$$
Tutti gli altri componenti $m \neq j$ e la resa complessiva $Y$ vengono immediatamente riparametrati:
$$Y^* = Y_{\text{base}} \cdot k^*, \qquad \forall m \in \text{Componenti}, \quad q^*(m) = q_{\text{base}}(m) \cdot k^*$$

\subsection{Quantizzazione e Sistema delle Unit\`a di Misura}
In gastronomia e pasticceria non tutte le grandezze possono essere trattate come numeri reali continui in $\mathbb{R}^+$. L'architettura classifica le unit\`a $\mathcal{U}$ in tre categorie ortogonali:
\begin{enumerate}
    \item \textbf{Unit\`a Continue Ponderali e Volumetriche ($g, kg, ml, l$):} I valori scalati mantengono fino a due cifre decimali se $q < 100$, oppure vengono approssimati al numero intero se $q \ge 100$ per uniformit\`a con le bilance digitali professionali.
    \item \textbf{Unit\`a Discrete Quantizzate ($pezzi; unit\grave{a}$):}
    $$\text{roundIntegerAmount}(q) = \max(1; \lfloor q + 0.5 \rfloor)$$
    Nel caso specifico delle uova intere o dei tuorli, un valore come 2.4 unit\`a non \`e utilizzabile direttamente senza creare sprechi. La quantizzazione arrotonda all'intero pi\`u prossimo salvaguardando il minimo di 1 unit\`a.
    \item \textbf{Quantificatori Qualitativi ($q.b.$):} Non sono soggetti a moltiplicazione scalare e mantengono costantemente la dicitura letterale ``q.b.''.
\end{enumerate}

\subsection{Modello Analitico del Food Cost}
Sia $P(i)$ il prezzo per unit\`a di misura associato all'ingrediente $i$. Il costo elementare $C(c)$ del componente scalato $c$ con quantit\`a $q(c)$ e unit\`a $u_r$, dato un prezzo $p$ con unit\`a $u_p$, \`e formalizzato come:
$$C(c) = q(c) \cdot \mu(u_r; u_p) \cdot p$$
Dove $\mu(u_r, u_p)$ \`e l'operatore di conversione metrica:
$$
    \mu(u_r; u_p) = 
    \begin{cases}
        1 & \text{se } u_r = u_p \lor (u_r \in \{g, ml\} \land u_p \in \{g, ml\}) \lor (u_r \in \{kg, l\} \land u_p \in \{kg, l\}) \\
        10^{-3} & \text{se } u_r \in \{g, ml\} \land u_p \in \{kg, l\} \\
        10^3 & \text{se } u_r \in \{kg, l\} \land u_p \in \{g, ml\} \\
        \frac{\text{gramsPerUnit}}{1000} & \text{se } u_r \in \{\text{unit\`a, pz}\} \land u_p = kg \\
        \text{gramsPerUnit} & \text{se } u_r \in \{\text{unit\`a, pz}\} \land u_p = g \\
        0 & \text{se } u_r = \text{q.b.}
    \end{cases}
$$
Nel contesto della ricetta, un ingrediente la cui dose \`e qualificata come \textit{q.b.} (quanto basta) presenta $C(c) = 0$, trattandosi di un dosaggio non ponderale a discrezione dello chef (ad es. un pizzico di sale o spezie) che non deve alterare artificiosamente il costo base del lotto di produzione.

Il costo totale dell'impasto $C_{\text{totale}}$ e il costo unitario per porzione $C_{\text{porzione}}$ si ottengono mediante accumulazione ricorsiva bottom-up:
$$C_{\text{totale}} = \sum_{c \in \text{Foglie}} C(c) + \sum_{s \in \text{Sotto-Ricette}} C_{\text{totale}}(s)$$
$$C_{\text{porzione}} = \frac{C_{\text{totale}}}{Y_{\text{target}}}$$

\subsection{Coerenza Metrica tra Food Cost e Carrello della Spesa}
L'aggregazione degli ingredienti nella lista della spesa adotta l'identico operatore di conversione metrica $\mu(u_r, u_p)$. In questo modo, un ingrediente con costo espresso al chilogrammo (es. \euro\,1.80/kg) la cui ricetta richiede 250\,g produce nel carrello della spesa una stima pari a:
$$\text{Costo}_{\text{spesa}} = 250 \cdot 10^{-3} \cdot 1.80 = 0.45\,\text{\euro}$$
eliminando qualsiasi discrepanza tra il Food Cost stimato nel dettaglio ricetta e la spesa complessiva.

Per gli ingredienti a quantitativo qualitativo indeterminato (\textit{q.b.}), la lista della spesa eredita l'unit\`a di misura associata al prezzo d'acquisto ($u_p$) e adotta una quantit\`a deterministica standard per consentire l'approvvigionamento del formato commerciale minimo:
$$
q_{\text{spesa}} = 
\begin{cases}
    100 & \text{se } u_p \in \{\text{g}, \text{ml}\} \\
    1 & \text{per unit\`a discrete o formati commerciali (pz, unit\`a)}
\end{cases}
$$
fornendo all'utente un punto di partenza facilmente calibrabile direttamente dalla checklist d'acquisto.

\subsection{Tipografia e Algoritmo di Line-Breaking Antifrattura}
Nella presentazione delle stringhe descrittive complesse degli ingredienti (specialmente denominazioni protette quali \textit{Formaggio Parmigiano Reggiano DOP} o \textit{Olio Extravergine d'Oliva}), l'algoritmo di rendering di Jetpack Compose \`e stato vincolato per inibire la sillabazione infrasillabica (\texttt{Hyphens.None}) e forzare il wrapping esclusivamente sui delimitatori di parola (\texttt{LineBreak.Paragraph}). Ci\`o previene la frammentazione antiestetica dei lemmi merceologici sui display a densit\`a variabile.

\subsection{Stabilit\`a Tipografica dei Badge Allergeni e Prevenzione della Compressione Orizzontale}

\begin{enumerate}

\subsection{Equivalenza Culinaria Massa-Volume ($1:1$) nel Food Cost e nella Spesa}
Nell'esperienza gastronomica quotidiana, molti ingredienti fluidi o semi-densi (acqua, latte, succhi, infusi, brodi, caff\`e, panna liquida, ecc.) vengono misurati indifferentemente in volume ($ml, l$) o in peso ($g, kg$). L'operatore di conversione $\mu(u_r; u_p)$ integra il principio di \textbf{equivalenza culinaria isotropa}:
$$1\,\text{g} \equiv 1\,\text{ml}, \qquad 1\,\text{kg} \equiv 1\,\text{l}$$
In questo modo, se un ingrediente viene dosato in millilitri (es. $300\,\text{ml}$ di latte o caff\`e) ma il listino d'acquisto \`e espresso al chilogrammo (es. \euro\,$25.00/\text{kg}$), il costo elementare non genera anomalie di scala n\'e moltiplicazioni improprie:
$$C = 300\,\text{ml} \cdot 10^{-3} \cdot 25.00 = 7.50\,\text{\euro}$$
L'aggregatore della lista della spesa applica la medesima equivalenza, garantendo coerenza assoluta tra magazzino, preventivo economico e quantit\`a da acquistare.

\subsection{Modello Matematico della Variazione di Massa in Cottura (Resa Termica)}
Durante la trasformazione termica, la massa complessiva della preparazione si modifica in funzione del parametro \texttt{cookingWeightModifier} ($\Delta M \in [-100, +\infty)\,$):
\begin{definition}[Massa Cruda e Massa Cotta Finita]
Sia $W_{\text{raw}}$ la massa totale dell'impasto a crudo, calcolata come sommatoria dei pesi di tutti gli ingredienti ponderali ($g, kg$) o convertibili ($ml, l$):
$$W_{\text{raw}} = \sum_{c \in \text{Foglie}} q_{\text{scaled}}(c) \cdot \rho(u_c)$$
dove $\rho(u_c) = 1$ per grammi e millilitri, $\rho(u_c) = 1000$ per chilogrammi e litri, e $\rho(u_c) = \text{gramsPerUnit}$ per unit\`a discrete.
La massa cotta finita $W_{\text{cooked}}$ \`e definita come:
$$W_{\text{cooked}} = W_{\text{raw}} \cdot \left(1 + \frac{\Delta M}{100}\right)$$
\end{definition}

Si distinguono tre regimi termodinamici:
\begin{itemize}[leftmargin=*]
    \item \textbf{Calo Peso Termico ($\Delta M < 0$):} Evaporazione d'acqua per torte da forno, crostate, panificati e arrosti (es. $\Delta M = -10\% \implies W_{\text{cooked}} = 0.90 \cdot W_{\text{raw}}$);
    \item \textbf{Idratazione e Aumento di Massa ($\Delta M > 0$):} Assorbimento di brodo o acqua di cottura da parte di amidi e cereali secchi (es. pasta secca $\Delta M = +120\% \implies W_{\text{cooked}} = 2.20 \cdot W_{\text{raw}}$);
    \item \textbf{Regime Neutro ($\Delta M = 0$):} Preparazioni fredde, salse crude, cocktail o gelati dove non vi \`e perdita n\'e guadagno di solvente volatile.
\end{itemize}

Il peso finito cotto di ciascuna porzione \`e dato da:
$$w_{\text{portion, cooked}} = \frac{W_{\text{cooked}}}{N_{\text{portions}}}$$

\subsection{Modello di Calcolo della Dichiarazione Nutrizionale UE (Regolamento UE n. 1169/2011)}
Ciascuna materia prima $i \in V_{\text{raw}}$ possiede un vettore nutrizionale intrinseco a crudo riferito a $100\,\text{g}$:
$$\mathbf{Nut}_i = \begin{pmatrix} E_i \\ C_i \\ F_i \\ P_i \\ W_i \\ S_i \end{pmatrix} = \begin{pmatrix} \text{Energia (kcal)} \\ \text{Carboidrati (g)} \\ \text{Grassi (g)} \\ \text{Proteine (g)} \\ \text{Acqua/Umidit\`a (g)} \\ \text{Sodio (mg)} \end{pmatrix}$$
L'Energia in kiloJoule viene calcolata secondo il fattore di conversione standard UE:
$$E_{\text{kJ}} = E_{\text{kcal}} \times 4.184$$
La quantit\`a equivalente di \textbf{Sale (g)} \`e formalizzata dal Regolamento UE 1169/2011 moltiplicando il Sodio (espresso in grammi) per la costante stechiometrica del cloruro di sodio ($2.5$):
$$\text{Sale (g)} = \frac{Sodio_{\text{mg}}}{1000} \times 2.5$$

La quantit\`a assoluta totale di ciascun nutriente nella ricetta prima della cottura \`e:
$$\mathbf{Nut}_{\text{tot}} = \sum_{c \in \text{Componenti}} \frac{q_{\text{grams}}(c)}{100} \cdot \mathbf{Nut}_c$$

\subsection{Algoritmo di Concentrazione e Diluizione Nutrizionale Post-Cottura}
\begin{theorem}[Fattore di Concentrazione Nutrizionale sulla Resa Cotta]
Dato che i macronutrienti (grassi, proteine, carboidrati) e i micronutrienti minerali (sodio/sale) non subiscono evaporazione a temperature di cottura ordinarie ($\le 250^\circ\text{C}$), la massa assoluta dei nutrienti si conserva: $\mathbf{Nut}_{\text{tot, cooked}} = \mathbf{Nut}_{\text{tot, raw}}$.
Pertanto, la concentrazione di ciascun nutriente per $100\,\text{g}$ di prodotto finito cotto \`e funzione inversa della massa cotta:
$$\mathbf{Nut}_{\text{cooked}}^{100g} = \frac{\mathbf{Nut}_{\text{tot}}}{W_{\text{cooked}}} \times 100 = \frac{\mathbf{Nut}_{\text{tot}}}{W_{\text{raw}} \cdot \left(1 + \frac{\Delta M}{100}\right)} \times 100$$
\end{theorem}
\begin{proof}
Se $\Delta M < 0$ (evaporazione dell'acqua), il denominatore decresce ($W_{\text{cooked}} < W_{\text{raw}}$), determinando un aumento della densit\`a calorica e nutrizionale per 100 grammi (effetto di concentrazione). Viceversa, se $\Delta M > 0$ (assorbimento d'acqua), il denominatore cresce, inducendo una diluizione della densit\`a nutrizionale per 100 grammi. In entrambi i casi, l'apporto nutrizionale \textbf{per porzione} rimane invariato rispetto al totale:
$$\mathbf{Nut}_{\text{portion}} = \frac{\mathbf{Nut}_{\text{tot}}}{N_{\text{portions}}}$$
\end{proof}

\subsection{Regole di Conservazione Gastronomica dell'Unit\`a di Resa}
Per prevenire conversioni inappropriate operate dai modelli linguistici (ad es. forzare a ``porzioni'' preparazioni con resa unitaria intrinseca), il motore impone le seguenti regole deterministiche:
\begin{itemize}[leftmargin=*]
    \item Se l'unit\`a inserita dall'utente appartiene all'insieme dei descrittori ammissibili per la classe di ricetta (es. \textit{torta, crostata} per categoria Dolci; \textit{bicchieri, calici, tazze} per Caffetteria o Drink; \textit{panini, burger} per la categoria Panini; \textit{teglia, pizza} per Pizze), il generatore AI \`e vincolato contrattualmente a preservare fedelmente tale unit\`a;
    \item Solo in caso di incompatibilit\`a semantica manifesta (es. \textit{bicchieri} per un arrosto di carne o per un risotto), il sistema applica il fallback sicuro al formato generico ``porzioni''.
\end{itemize}

\subsection{Prevenzione dei ``Dangling Pointers'' Relazionali}
Uno dei punti pi\`u delicati dell'architettura riguarda l'eliminazione di una ricetta utilizzata come ingrediente in altre preparazioni.
\begin{secbox}[Politica di Eliminazione Sicura]
Se l'utente elimina la ricetta $R$, ma $R$ \`e utilizzata in $P_1, P_2, \dots, P_n$:
\begin{enumerate}
    \item La tupla corrispondente viene cancellata dalla tabella \texttt{recipes};
    \item I suoi componenti interni come genitore vengono rimossi da \texttt{recipe\_components};
    \item \textbf{L'entit\`a in \texttt{items} non viene eliminata}, bens\`i convertita atomicamente da \texttt{type = "RECIPE"} a \texttt{type = "RAW\_INGREDIENT"}.
\end{enumerate}
In questo modo, le ricette genitori $P_1, \dots, P_n$ continuano a funzionare regolarmente considerando $R$ come una materia prima acquistabile/pre-composta, senza generare eccezioni di puntatore nullo o corruzioni nel grafo!
\end{secbox}

suspend fun deleteRecipe(recipeId: String, convertToRaw: Boolean = false): DeleteResult {
    return try {
        val referencing = recipeDao.getParentRecipeNamesUsingChild(recipeId)

                itemDao.deleteItemById(recipeId)
            }

}

\subsection{Algoritmo di Riordinamento Reattivo Continuo (Drag \& Drop) e Spostamento Discreto}
Nel modulo di composizione della ricetta (\texttt{RecipeEditScreen}), l'ordinamento sequenziale degli ingredienti risponde a due modalit\`a operative:
\begin{enumerate}
    \item \textbf{Spostamento Discreto a Passo Singolo:} I metodi \texttt{moveComponentUp(index)} e \texttt{moveComponentDown(index)} operano scambi puntuali tra indici adiacenti su lista immutabile (\texttt{toMutableList().apply \{ Collections.swap(...) \}}).
    \item \textbf{Trascinamento Continuo Multi-Posizione (Fluid Drag \& Drop):} L'implementazione convenzionale dei pointer gesture detector in Compose (\texttt{detectDragGesturesAfterLongPress}) acquisisce per chiusura lessicale (\textit{closure capture}) l'indice dell'elemento all'avvio del tocco; ci\`o comportava l'arresto dello scorrimento dopo un singolo scambio.
\end{enumerate}

Per consentire lo scorrimento continuo dall'inizio alla fine dell'elenco senza mai sollevare il dito, \`e stato implementato un automa dinamico a stato reattivo:
\begin{lstlisting}[caption={Algoritmo continuo multi-slot basato su ID dinamico e loop iterativo}]
var activeDragId by remember { mutableStateOf<String?>(null) }
var dragOffsetY by remember { mutableFloatStateOf(0f) }
val itemSlotHeightPx = with(LocalDensity.current) { 80.dp.toPx() }

// All'interno di pointerInput(comp.tempId):
detectDragGesturesAfterLongPress(
    onDragStart = { activeDragId = comp.tempId; dragOffsetY = 0f },
    onDrag = { _, dragAmount ->
        dragOffsetY += dragAmount.y
        // Spostamento verso il basso (multi-slot)
        while (dragOffsetY > itemSlotHeightPx) {
            val list = viewModel.uiState.value.components
            val curIdx = list.indexOfFirst { it.tempId == activeDragId }
            if (curIdx != -1 && curIdx < list.size - 1) {
                viewModel.moveComponent(curIdx, curIdx + 1)
                dragOffsetY -= itemSlotHeightPx
            } else break
        }
        // Spostamento verso l'alto (multi-slot)
        while (dragOffsetY < -itemSlotHeightPx) {
            val list = viewModel.uiState.value.components
            val curIdx = list.indexOfFirst { it.tempId == activeDragId }
            if (curIdx != -1 && curIdx > 0) {
                viewModel.moveComponent(curIdx, curIdx - 1)
                dragOffsetY += itemSlotHeightPx
            } else break
        }
    },
    onDragEnd = { activeDragId = null; dragOffsetY = 0f },
    onDragCancel = { activeDragId = null; dragOffsetY = 0f }
)
\end{lstlisting}

L'algoritmo calcola in tempo reale la posizione corrente dell'\texttt{activeDragId} nello StateFlow immutabile, decrementando o incrementando iterativamente l'accumulatore \texttt{dragOffsetY} in quanti multipli dell'altezza di slot (\texttt{itemSlotHeightPx}). L'esperienza visiva \`e resa continua tramite accelerazione hardware con \texttt{Modifier.graphicsLayer \{ translationY = dragOffsetY; scaleX = 1.02f; scaleY = 1.02f \}} ed elevazione su layer prioritario con \texttt{Modifier.zIndex(10f)}.

    \item \textbf{Algoritmo Cifrante:} \texttt{AES} (Advanced Encryption Standard);
    \item \textbf{Dimensione Chiave:} 256 bit ($32\,\text{byte}$);
    \item \textbf{Modalit\`a di Blocco:} \texttt{GCM} (Galois/Counter Mode);
    \item \textbf{Padding:} \texttt{NoPadding};
    \item \textbf{Autenticazione Tag:} 128 bit ($16\,\text{byte}$).
\end{itemize}

\begin{secbox}[Propriet\`a Hardware-Bound e Non-Esportabilit\`a]
Le master key con alias \texttt{simo\_gemini\_master\_key} e \texttt{simo\_openai\_master\_key} sono generate con il parametro:
\begin{center}
\texttt{setRandomizedEncryptionRequired(true)}
\end{center}
La chiave non pu\`o mai lasciare il chip di sicurezza hardware. Se l'utente esporta un backup o se i dati dell'applicazione vengono clonati su un altro dispositivo, il token cifrato risulter\`a matematicamente indecifrabile (\texttt{AEADBadTagException}), garantendo l'assoluta impossibilit\`a di esfiltrazione delle credenziali.
\end{secbox}

private fun getOrCreateSecretKey(): SecretKey {

\subsection{Macchina a Stati dei Timer Concorrenti e Architettura Persistente}
Per garantire che il conto alla rovescia non subisca drift temporale o azzeramenti imprevisti quando l'applicazione viene posta in background (ad esempio durante l'ascolto o la visione di video su YouTube, o a fronte della liberazione della memoria di processo da parte dell'OS), la gestione temporale \`e disaccoppiata dal ciclo di refresh della UI e ancorata a timestamp assoluti di sistema.

I timer attivi sono modellati mediante la data class \texttt{ActiveKitchenTimer}:
\begin{lstlisting}[caption={Modello dati immutabile del timer con epoch timestamp assoluto}]
data class ActiveKitchenTimer(
    val id: String = UUID.randomUUID().toString(),
    val label: String,
    val totalSeconds: Int,
    val remainingSeconds: Int = totalSeconds,
    val isRunning: Boolean = true,
    val isFinished: Boolean = false,
    val endTimeMillis: Long = System.currentTimeMillis() + (totalSeconds * 1000L),
    val pausedRemainingSeconds: Int? = null
) {
    fun currentRemainingSeconds(): Int {
        if (isFinished) return 0
        return if (!isRunning) {
            pausedRemainingSeconds ?: remainingSeconds
        } else {
            val remaining = ((endTimeMillis - System.currentTimeMillis()) / 1000).toInt()
            Math.max(0, remaining)
        }
    }
}
\end{lstlisting}

\begin{lstlisting}[caption={Word-wrapping dinamico su Canvas}]
private fun drawWrappedText(
    canvas: Canvas,
    text: String,
    x: Float,
    startY: Float,
    maxWidth: Float,
    paint: Paint,
    lineSpacing: Float
): Float {
    var currentY = startY
    val words = text.split(" ")
    var currentLine = StringBuilder()

    for (word in words) {
        val testLine = if (currentLine.isEmpty()) word else "$currentLine $word"
        val measuredWidth = paint.measureText(testLine)
        if (measuredWidth > maxWidth && currentLine.isNotEmpty()) {
            canvas.drawText(currentLine.toString(), x, currentY, paint)
            currentY += lineSpacing
            currentLine = StringBuilder(word)
        } else {
            currentLine = StringBuilder(testLine)
        }
    }
    if (currentLine.isNotEmpty()) {
        canvas.drawText(currentLine.toString(), x, currentY, paint)
        currentY += lineSpacing
    }
    return currentY
}
\end{lstlisting}

    \item \textbf{Conformit\`a e Sicurezza:} Piena aderenza alla normativa UE 1169/2011 per gli allergeni e standard crittografico hardware-backed AES-256 GCM conforme ai requisiti OWASP Mobile Security.
\end{itemize}

\subsection{Miglioramenti Futuri}
Questa applicazione pu\`o essere ulteriormente migliorata aggiungendo ulteriori feature:
\begin{enumerate}
	\item \textbf{Versione in Inglese:} Aggiunge un'impostazione per la lingua inglese in modo che l'app sia utilizzabile da più persone possibile; 
	\item \textbf{Integrazione Immagini:} Aggiunta di un supporto visivo per identificare rapidamente le ricette e implementazione dell'Intelligenza Artificiale per riconoscere ed estrarre preparazioni direttamente da una fotografia;
	\item \textbf{Integrazione Comandi Vocali:} Utilizzando la voce sarà possibile inserire ricette, ma soprattutto interagire durante la Cooking Mode,
	\item \textbf{Gestione Avanzata della Dispensa:} Filtro ricette realizzabili in tempo reale in base alle scorte disponibili, con modalit\`a "svuota-frigo" assistita da AI per abbattere gli sprechi ed import automatico dagli articoli spuntati nella lista della spesa;
	\item \textbf{Supporto Esteso a Nuovi Provider AI (Claude \& DeepSeek):} Ulteriore arricchimento dell'architettura modulare bivalente per connettere modelli alternativi offline od on-premise;
	\item \textbf{Integrazione Bilance Bluetooth Low Energy (BLE):} Interfacciamento diretto con le bilance da banco per l'acquisizione automatica del peso dell'ingrediente selezionato in Cooking Mode;
	\item \textbf{Sincronizzazione Multi-Dispositivo Crittografata:} Estensione del backup verso archivi cloud end-to-end encrypted (E2EE) per la condivisione istantanea tra stazioni di lavoro e cucine multiple.
\end{enumerate}
